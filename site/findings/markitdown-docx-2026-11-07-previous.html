microsoft/markitdown

Can MarkItDown convert a locally created Word document with a heading and table into Markdown that preserves both structures, without an LLM API?

Public trace redactions: Local account name in Docker socket error paths was redacted. Findings and command outcomes are unchanged; the original local database is preserved.

Stored verdict: inconclusive · 2026-09-26T02:49:15.525247+00:00

MarkItDown's docx conversion is designed as a local pipeline (docx -> HTML -> markdown via the project's own HtmlConverter) with no LLM client involved by default. The html-to-markdown half of that pipeline was directly verified in this session to preserve a heading and a table when run on a representative HTML snippet, with no LLM call made. However, the actual end-to-end conversion of a real, freshly created .docx file was not completed: MarkItDown's installed DocxConverter raised a MissingDependencyException, and the attempt to install the missing dependency (mammoth) timed out due to no sandbox network access. Docker-based sandbox tools were also unavailable throughout. As a result, whether headings and tables in a real .docx file survive MarkItDown's actual conversion pipeline end-to-end was not directly demonstrated, only inferred from separately testing the two halves.

Evidence ledger

reported · _docx_converter.py imports the project's own HtmlConverter and a pre_process_docx utility, and the portion of the file that was retrieved contains no reference to an LLM client or API key; however the middle of the file was omitted from the retrieved output, so the exact library used to convert the raw .docx XML to HTML is not confirmed from this evidence alone.
read_file(packages/markitdown/src/markitdown/converters/_docx_converter.py)

reported · The project's regression test vectors for its sample test.docx file (_test_vectors.py) assert the converted markdown must include '# Abstract' and '# Introduction', indicating Word heading styles are expected to become Markdown '#' headings.
read_file(packages/markitdown/tests/_test_vectors.py)

reported · test_docx_styles.py tests only that DOCX stylesheet XML namespace-qualified attributes are preserved during a preprocessing step; it does not test heading or table conversion and does not mention '# Abstract' or any markdown output.
read_file(packages/markitdown/tests/test_docx_styles.py)

reported · Attempting to run MarkItDown's actual DocxConverter on a freshly created .docx file (built with python-docx) raised a MissingDependencyException stating the dependencies needed to read .docx files were not installed, even though python-docx itself was present; the real end-to-end docx-to-markdown pipeline was not successfully executed in this session.
code_execution(docx conversion attempt on /tmp/test.docx)

reported · An attempt to pip install the missing dependency (mammoth) timed out after 30 seconds, apparently due to lack of network access in the sandbox, so the missing dependency could not be installed to unblock the real pipeline.
code_execution(pip install mammoth)

reported · Running the project's own HtmlConverter.convert_string() on a hand-authored HTML snippet representing a heading and a table (used as a stand-in for what mammoth's HTML output would look like, not actual output from the created .docx file) produced correct Markdown: a '#' heading and a pipe-delimited table, with no LLM call made.
code_execution(HtmlConverter.convert_string heading and table html)

Recorded limitations

  • The full docx-to-markdown pipeline was never successfully run on a real .docx file in this session; MarkItDown's DocxConverter raised a MissingDependencyException, and installing the missing dependency (mammoth) timed out due to no sandbox network access.
  • The Docker-based sandbox tools were unavailable throughout the session, so verification relied on ad hoc code execution in a possibly non-standard environment rather than a clean install matching the repo's documented setup.
  • The html-to-markdown heading/table check used a hand-written HTML snippet as a stand-in for what mammoth would actually produce from the created .docx file, rather than mammoth's real output, so the fidelity of the docx-to-HTML conversion step itself was not verified.
  • The one test file inspected for docx-specific behavior (test_docx_styles.py) covers only XML stylesheet attribute preservation, not heading or table conversion, so no project test was directly confirmed to validate heading+table preservation end-to-end from a real docx.
